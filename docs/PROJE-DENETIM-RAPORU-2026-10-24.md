### A1 · Idempotency middleware commits the tracked changes of a failed request (product-cost apply saves part of the file after answering 409 'nothing saved')

- **Önem:** Yüksek · **Tür:** data · **Güven:** high
- **Yer:** `src/MarketplaceHub.Api/Catalog/IdempotencyMiddleware.cs:182`
- **Senaryo:** The seller previews a cost file with variants A (v3) and B (v5). Before Apply, B's cost is edited in the product editor (B becomes v6). Apply runs with a required Idempotency-Key. ProductCostService.ApplyAsync (ProductCostService.cs:127-140) loops in order: it sets A.CostPrice, UpdatedAt and Version++ on the tracked entity, then reaches B, sees the version mismatch and returns Stale 409 without saving. Control returns to IdempotencyMiddleware, which shares the same scoped AppDbContext. Because 409 < 500 it marks the record COMPLETED and calls db.SaveChangesAsync(CancellationToken.None) (line 182). That save also writes variant A's new cost. The user sees 'önizlemeden sonra değişti; dosyayı yeniden yükleyin' and believes nothing was written, but A's cost changed, with no PRODUCT_COSTS_IMPORTED audit row. The existing test ProductCostImportTests.cs:252 sends a single stale change straight to the service without the middleware, so it cannot catch this.
- **Etkisi:** Wrong product costs, and so wrong profit and margin figures on the reports page. The change has no audit trail and contradicts the message shown. The same path affects every endpoint behind an Idempotency-Key whose service changes tracked entities and then returns a 4xx without saving: the middleware saves what a refusal left behind.
- **Çözüm:** After next(context), save only the idempotency record. Detach every other tracked entry before line 182, as MarkUnknownAsync already does at lines 228-229. Alternatively, write the record's final state with ExecuteUpdateAsync by Id instead of SaveChangesAsync. Separately, ProductCostService.ApplyAsync should check every version before changing any entity, or call ChangeTracker.Clear() before returning Stale. Add an endpoint-level test that runs the stale apply through the middleware with two changes.
- **Doğrulama:** Confirmed by reading the code. ProductCostService.ApplyAsync (src/MarketplaceHub.Infrastructure/Persistence/ProductCostService.cs:127-140) loads the variants as tracked entities. It changes CostPrice, UpdatedAt and Version on each variant in turn, then returns Stale (409) at the first version mismatch without saving and without calling ChangeTracker.Clear(). Clear() is called only in the DbUpdateConcurrencyException branch. AppDbContext is scoped (AddDbContext, DependencyInjection.cs:34), so the IdempotencyMiddleware instance and ProductCostService share it. The apply endpoint is POST /api/v1/products/costs/apply and requires Idempotency-Key (ProductCostEndpoints.cs:60), so the middleware always wraps it. After next(), any status below 500 goes to record.State=COMPLETED and a plain db.SaveChangesAsync (IdempotencyMiddleware.cs:182). That save flushes the earlier variants' changes. Their Version concurrency check passes because nothing else changed them. No audit row is written, because the AuditLog is added only after the loop. Only MarkUnknownAsync (status 500 or an exception) and ForgetAsync detach other tracked entries; the 4xx path does not. None of the earlier reports (2026-10-19, 2026-10-20, TEKNIK-DUZELTME) cover the 4xx path. TEKNIK-DUZELTME notes the 500 path as fixed, which is why that path is protected. Trigger: an editor change between preview and apply to a variant listed after another changed variant. Plausible during normal use. The pattern also affects any other keyed endpoint that refuses with a 4xx after changing tracked entities. Severity stays high: silent wrong costs and margins, and a 409 'nothing written' message that is false.

### S1 · Kısmen iptal edilen PTT AVM ve Pazarama siparişleri paket miktar kontrolünde tümüyle reddediliyor

- **Önem:** Yüksek · **Tür:** data · **Güven:** high
- **Yer:** `src/MarketplaceHub.Infrastructure/Adapters/PttAvm/PttAvmOrderMapper.cs:74`
- **Senaryo:** Bir PTT AVM siparişinde iki satır var: A satırının durumu 'iptal', B satırınınki 'kargo_yapilmasi_bekleniyor'.
